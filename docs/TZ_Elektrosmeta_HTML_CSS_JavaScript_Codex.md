# Техническое задание для Codex: «Электросмета»

План электрики, материалы, щит и смета.

Версия: 1.0. Дата: 16.10.2026. Язык приложения: русский.
Целевая реализация: HTML5 + CSS3 + JavaScript, адаптивное веб-приложение с офлайн-работой.

Документ предназначен для передачи Codex вместе с файлом PROMPT_CODEX_Elektrosmeta.txt. Он описывает реализацию, а не сообщает о наличии готового приложения. Источник требований: сохранённый документ «PROMPT_ТЗ_Электросмета_для_GPT6.md» от 08.10.2026 и текущая просьба подготовить ТЗ для HTML, CSS и JavaScript. Выбранный здесь веб-стек заменяет прежний вариант Kotlin/Compose для этой реализации; предметные требования сохранены.

## 1. Цель и результат

Создать рабочий инструмент электрика для встречи с заказчиком и подготовки электромонтажных работ в квартире, доме или отдельном помещении.

Пользователь создаёт объект, рисует план в реальных размерах, размещает точки и приборы, назначает линии, рисует кабельные трассы и штробы. Приложение рассчитывает геометрию, нагрузки, состав щита, объёмы работ, материалы и стоимость. Пользователь проверяет результат и скачивает клиентский PDF с перечнем работ, объёмами и одной итоговой суммой.

Обязательны два полноценных режима:

- «Быстрая смета»: ручной ввод объёмов по короткому прайсу без обязательного плана.
- «Смета по плану»: автоматическое получение объёмов из проекта с явными ручными корректировками.

Результат разработки — запускаемый исходный проект, локальные зависимости и шрифты, демонстрационный объект, тесты расчётов, инструкция запуска и протокол проверки. Красивый макет без работающих расчётов не является результатом.

### 2.2. За пределами этой реализации

Нативные APK/IPA и публикация в магазинах; серверная авторизация и совместная работа; облачная синхронизация; платежи; маркетплейс «Прораб»; интеграции VK/Telegram; распознавание плана нейросетью; полноценный BIM/CAD; 3D; выпуск юридически удостоверенного электропроекта; измерения электроустановки программными средствами.

Импорт чертежей DWG/DXF и автоматическая трассировка всего объекта не входят в v1. Полноценные автоматические расчёты короткого замыкания и селективности не подменять имитацией: их статус должен быть «Не проверено», если нет исходных данных и реализованного метода.

### 2.3. Роль

Один локальный пользователь — электрик. «Вид для заказчика» является способом представления сметы, а не отдельной учётной записью. Клиентский PDF формируется из отдельной публичной модели данных без внутренних расценок.

## 3. Основные сценарии

### 3.1. Быстрая смета

«Новый объект» → карточка → «Быстрая смета» → объёмы, цены и материалы → «Рассчитать» → проверка → «Сохранить смету» → «Скачать PDF».

Расчёт обновляется также при изменении данных. Кнопка «Рассчитать» проверяет ввод, пересчитывает итог и показывает результат; кнопка PDF является отдельным действием. Режим работает без стен, точек и линий.

### 3.2. Смета по плану

Карточка объекта → сеть и сложность → план → точки и приборы → линии → кабели и трассы → штробы → щит → «ОК — рассчитать» → проверка → автоматические объёмы → корректировки → итог → снимок сметы → PDF.

«ОК» сохраняет изменения плана и запускает предметный расчёт. Ошибки конкретного модуля не уничтожают план и не мешают сохранить черновик.

### 3.3. Возвращение к объекту

Поиск → открыть объект → продолжить черновик или открыть сохранённую версию сметы. Изменение плана не переписывает ранее сохранённую смету и выпущенный PDF. Новая смета получает новый номер версии.

На устройствах без установки PWA приложение работает во вкладке. Наличие системного меню отправки PDF определяется через feature detection, скачивание остаётся доступным.

В инструкции дать запуск статического сервера, например python -m http.server 8080, и открытие http://localhost:8080. По ссылке пользователя работает статический сайт без установки Docker или Android SDK. Публичное размещение не выполнять без отдельной задачи пользователя.

## 6. Единицы и принятые значения

### 6.1. Внутренние единицы

Координаты, длины и высоты — целые миллиметры; мощность — Вт; напряжение — В; ток — А; сечение — мм²; масса — кг; жидкость — л; площадь — м²; деньги — целые копейки. ID — UUID или эквивалентные устойчивые уникальные строки. Даты создания и изменения — ISO UTC; дата сметы — отдельная календарная YYYY-MM-DD без сдвига часового пояса.

Числовой парсер принимает 2,5 и 2.5, отбрасывает пробелы-разделители, проверяет конечность и диапазон. Пустое значение является null, а не нулём. Отрицательные длины, количества, цены и мощности запрещены. Ноль допустим для цены только при явно подтверждённой бесплатной позиции.

Округление для расчётных количеств выполнять после суммирования по виду работы или SKU. Погонные объёмы работ — до 0,01 м по HALF_UP; закупка кабеля/гофры — вверх до 0,1 м; штучные позиции — целые; расходные жидкости/смеси — вверх до 0,01 л/кг до учёта фасовки. Не округлять каждый сегмент перед суммированием. Физическую геометрию не заменять округлёнными отображаемыми значениями. Коэффициент сложности положительный, диапазон ввода v1 0,1–10; доли для денежных действий переводить в целочисленные базисные пункты или точные десятичные дроби.

Сеть выбирается как «220 В, 1 фаза» или «380 В, 3 фазы» с раздельными числовыми U_LN и U_LL. Начальные пары: 220/380 В. Доступен профиль 230/400 В и ручное значение. Не заменять выбранное напряжение молча. Для однофазной линии трёхфазного объекта использовать U_LN, для симметричной трёхфазной нагрузки — U_LL.

## 7. Редактор планировки

### 7.1. Геометрическая модель

Начало координат плана (0,0); X вправо, Y вниз; Z — высота от чистого пола вверх. Масштаб 1:1 означает реальные размеры модели, а не физический метр на экране. Камера хранит panX, panY и zoom отдельно от геометрии. screen = world * zoom + pan; обратное преобразование применяется до привязки.

Стена задаётся двумя узлами, толщиной, материалом, ролью конструкции и высотой. Помещение — замкнутый простой многоугольник со ссылками на граничные стены и собственной высотой. Общая стена соседних помещений существует один раз. Дверь/проём привязаны к стене, имеют смещение и ширину, не уменьшают длину стены как геометрического объекта. Для v1 достаточно прямолинейных стен и многоугольных помещений без кривых.

Обязательные действия: создать стену, замкнуть помещение, ввести точную длину, переместить узел, выбрать объект, редактировать параметры, удалить, дублировать точку, измерить расстояние, вписать план в экран.

При изменении длины стены по умолчанию фиксировать её начальный узел и перемещать конечный вдоль текущего направления. Общие узлы меняют все связанные стены; до подтверждения показать геометрический предпросмотр. Самопересечение помещения или схлопывание стены запрещает подтверждение. Новая площадь вычисляется по модели, а введённая вручную площадь карточки хранится отдельно с объяснением различия.

Точка, привязанная к стене, хранит wallId, расстояние от её начала и сторону. После изменения стены сохраняется физическое расстояние от начала; если длины недостаточно, точка получает конфликт привязки, а не исчезает. Связанные трассы получают состояние «Нужно обновить»; разрешён пересчёт концов с предпросмотром, скрытый пересчёт длины запрещён.

### 7.2. Управление

Мышь: выбор кликом, панорамирование средней кнопкой или инструментом «Рука», масштаб колесом относительно курсора, Escape отменяет инструмент, Delete удаляет выделенное с проверкой связей. Горячие клавиши не работают внутри текстового ввода. Ctrl/Cmd+Z и Shift+Ctrl/Cmd+Z — отмена/повтор.

Касания: один палец действует выбранным инструментом, два пальца — pan/pinch; при переходе ко второму касанию незавершённое размещение не подтверждается. Использовать Pointer Events и pointer capture. Ограничивать touch-action только областью редактора; формы и страница остаются прокручиваемыми.

Привязка к сетке, вершине стены и существующему узлу с экранным радиусом 10 px; приоритет: узел, стена, сетка. Доступен ручной точный ввод без привязки. Толщина выделения и значки остаются удобными для касания при любом масштабе.

### 7.3. Слои и история

Слои: стены/проёмы, помещения, силовые точки, освещение, слаботочка, линии, кабельные трассы, штробы, размеры и подписи/высоты. Скрытие слоя не удаляет объекты и не исключает их из расчёта. Исключение из расчёта — отдельный параметр с видимым обозначением.

Хранить минимум 100 команд Undo/Redo для текущего объекта. Перетаскивание считается одной командой, а не сотнями pointermove. Изменение числового поля — одна команда после подтверждения. История команд не обязана переживать закрытие браузера; сохранённые версии сметы обязаны.

При удалении стены, точки, линии или узла показывать список зависимостей. По умолчанию запрещать разрушение ссылок. Явное действие «Удалить с отвязкой» оставляет зависимые точки/кабели в черновике и создаёт ошибки для исправления; не переносить их на случайный объект.

## 8. Электрические точки и нагрузки

Типы: розетка, блок розеток, выключатель 1/2 клавиши, проходной, перекрёстный, светильник, бра, силовой вывод, щит, интернет/ТВ, произвольный потребитель. Приборы вроде бойлера или панели выбираются из библиотеки, а не зашиваются отдельными неизменяемыми электрическими типами.

Обязательные поля точки: id, type, roomId, xMm, yMm, mountCount, heightReference=floor|ceiling, heightValueMm, circuitId или null, label. Дополнительные: wallAttachment, loadIds, controlGroupId, note, excludedFromEstimate.

Для размещённой точки вычислять zMm: от пола — heightValueMm; от потолка — roomHeightMm − heightValueMm. Разрешены значения от 0 до высоты помещения. Изменение высоты помещения обновляет точки с потолочной базой и связанные длины после подтверждения. Без помещения точка получает явную высоту потолка из этажа/объекта.

Блок из трёх розеток — одна геометрическая точка, три механизма и три посадочных места. Установленная мощность определяется отдельными экземплярами нагрузок, а не числом рамок или графических значков.

LoadInstance ссылается на библиотечный прибор и хранит снимок имени, мощности, количества, фазности, cosφ и способа задания мощности. Можно задать нагрузку вручную без библиотеки. Один физический прибор имеет один loadId и не учитывается повторно через розетку и значок прибора. Удаление прибора из библиотеки не удаляет его экземпляры в проектах.

Неназначенная обычная розетка не равна нагрузке 0 Вт: designPowerW=null, требуется заданная расчётная нагрузка или явно выбранный и подписанный шаблон. Слаботочка исключается из расчётов силовой мощности и силового щита; работы и материалы слаботочки добавляются отдельными позициями.

Двухклавишный выключатель имеет два канала управления; проходной/перекрёстный — соответствующие связи controlConnections. Управляющая связь не создаёт дополнительную мощность. Длины физических кабелей задаются трассами. Не рассчитывать число жил и безопасность сложной схемы только по названию выключателя.

## 9. Библиотеки

### 9.1. Приборы

CRUD и архив: название, категория, activePowerW, quantity по умолчанию 1, supply=1ph|3ph, cosPhi или null, powerBasis=electricalInput|mechanicalOutput, efficiency для механической мощности, паспортный ток при наличии, примечание. Минимальный быстрый ввод — название и мощность; остальные поля открываются в расширенных параметрах.

Если неизвестен cosφ, приложение может показать оценку при cosφ=1 с пометкой допущения; это не проверенный расчёт аппарата. Для чисто активной нагрузки пользователь подтверждает cosφ=1. Для механической мощности без КПД результат электрического тока не считается определённым.

При изменении библиотеки уже размещённые приборы сохраняют свой снимок. Действие «Обновить приборы объекта» показывает изменения и требует подтверждения конкретного обновления, затем пересчитывает связанные линии. Старые версии смет сохраняются.

### 9.2. Материалы

Общие поля: id, category, name, unit, unitPriceKopecks|null, manufacturer, sku, packageSize|null, consumptionRules, archived, version. Единицы ограничены справочником: м, шт., кг, л, комплект. Переход между единицами только по явному коэффициенту.

Категории и дополнительные свойства:

- Кабель: марка, материал жил, число жил, сечение, тип изоляции, наличие PE, документ производителя и допустимые условия применения.
- Гофра: тип, диаметр, погонная единица, цена. Вариант «в гофре» задаётся для конкретного участка кабеля, а не автоматически для всей линии.
- Подрозетники: тип основания и посадочного места, единица шт.
- Автоматы, УЗО, дифавтоматы: ток, полюса, характеристика, дифференциальные параметры по типу, ширина в модулях и паспортные данные.
- Корпус щита, шины, клеммы, принадлежности: количество и модули при необходимости.
- Крепёж кабеля/гофры: тип узла, число поддерживаемых кабелей, метизы на узел.
- Метизы: тип, единица, норма на крепление/узел.
- Грунтовка: литры на м² и число слоёв.
- Гипсовая смесь: кг на м³ заполнения либо кг/м² при заданной толщине слоя; поддержать явное преобразование единиц.
- Прочие материалы: ручная строка с количеством и единицей.

Архивная позиция не предлагается для нового выбора, но остаётся в существующих проектах и снимках. Товарные параметры производителя и нормативный профиль расчёта — разные сущности. Изменение названия материала не должно автоматически менять его нормативную область применения.

## 10. Линии и физические кабели

Circuit: id, number, name, color, purpose, lineType=general|dedicated, supplyType=1ph|3ph, phase=L1|L2|L3|ABC|null, pointIds, loadIds, demandFactor, cableSpec, protectionRef, ruleProfileId, manualOverrides.

Показывать установленную мощность, расчётную нагрузку, ток, суммарную длину кабелей, число точек, тип защиты и статус. Цвет дополнять номером и подписью.

Пользователь создаёт линию, добавляет и переносит точки, разделяет линию и объединяет совместимые линии с предпросмотром последствий. Силовой loadId назначается ровно одной линии. Отдельная линия имеет одного потребителя или явную согласованную группу; приложение проверяет применимость по профилю, не объявляя универсального правила «любой мощный прибор — отдельный автомат».

Circuit — электрическая группа, CableRun — отдельный физический кабель между двумя узлами. Одна группа может содержать несколько физических кабелей и ответвления. Одна геометрическая трасса может нести несколько разных кабелей. Не смешивать эти сущности и не считать один участок кабеля только потому, что на плане отображена одна цветная линия.

CableRun: id, circuitId, fromNodeId, toNodeId, cableMaterialId, routeSegmentIds, slackStartMm, slackEndMm, cableReservePct. Узлами являются щит, точка, распределительный узел или обозначенный конец. Циклы и отсутствующие соединения проверять как топологию, при этом допустимые схемы управления освещением имеют отдельные явно описанные связи.

## 11. Трассы и способы прокладки

RouteSegment — физическая геометрия в XYZ, installation=open|chase|conduitInStructure|other, level=floor|ceiling|custom, hasConduit, conduitMaterialId|null, wallId|null, structuralRole, mountingGroupId|null, role=main|feed|switchedLighting|traveller|other. Элемент ссылается на один или несколько физически уложенных кабелей через назначения CableRun.

Способ «по полу/по потолку», открытость и наличие гофры являются независимыми свойствами. Кабель по потолку не всегда является открытым. Крепёж включается по installation=open, а не по слову «потолок».

Пользователь рисует полилинию с прямыми участками и точными координатами/высотами. Нужны разделение участка, перемещение вершины, добавление вертикального подъёма/опуска и редактирование числа физических кабелей. Разрешён ортогональный черновой маршрут между выбранными узлами; он требует подтверждения и не является автоматическим разрешением прокладки через конструкции.

### 11.1. Особое правило освещения

Участок от выключателя к светильнику с role=switchedLighting всегда имеет горизонтальную часть по потолку. Это требование пользователя к продукту, не универсальная ссылка на ПУЭ. Выбор основной трассы по полу его не меняет.

При высоте потолка H, выключателя hS и светильника hL маршрут включает подъём H−hS, горизонтальный путь по потолку и опуск H−hL. Если светильник расположен на потолке, последний участок равен 0. Питание до выключателя считается отдельным CableRun; оно не теряется и не считается второй раз как участок до светильника.

Для проходных схем пользователь задаёт физические кабели и связи; правило потолочного расположения выходного участка сохраняется. Конфликт при ручном рисовании показывается до подтверждения.

## 12. Расчёт длины кабеля

Для каждой полилинии: Lgeom_mm = Σ sqrt((Δx)² + (Δy)² + (Δz)²). Вертикальный участок явно задан изменением Z. Не прибавлять автоматически ту же высоту ещё раз после измерения 3D-полилинии.

Для физического кабеля j:

- Linstall_j = Lgeom_j — реальная длина монтажа.
- Lbase_j = Lgeom_j + slackStart_j + slackEnd_j.
- LpurchaseRaw_j = Lbase_j × (1 + cableReservePct_j / 100).

Итог материала одной марки/числа жил/сечения = сумма LpurchaseRaw_j по этим кабелям, затем округление вверх до 0,1 м. Не округлять до целых метров каждый короткий участок. Ведомость показывает отдельно монтажную длину, хвосты, запас и количество закупки.

Пример без хвостов: горизонтальная часть 12 400 мм, подъём 3200 мм, опуск 1400 мм. Lgeom=17 м. Запас 5%: 17,85 м; к закупке 17,9 м. Объём работы «Прокладка кабеля» = 17 м, а не 17,9 м.

Если по общему пути 5 м проложены два отдельных кабеля, кабеля 10 м. Длина одной штробы на этом пути может оставаться 5 м. Если несколько интерфейсных сегментов описывают один физический кабель без наложения, их длины складываются; дубли геометрии внутри CableRun не удалять молча, а обнаруживать как конфликт.

Гофра считается только на участках hasConduit=true, по каждому фактическому рукаву. Несколько кабелей в одном рукаве требуют одного conduitRunId; без явного объединения каждый кабель считается в своём рукаве. Её запас и фасовка рассчитываются отдельно от запаса кабеля.

## 13. Штробы

Chase: id, planeId/wallId, polylineXYZ, widthMm, depthMm, wallMaterial, structuralRole, fillAfterInstallation:boolean, primerMaterialId|null, fillerMaterialId|null, note. Размеры положительные; ширина и глубина не выводятся из сечения кабеля без явного инженерного решения.

Штроба — самостоятельная физическая работа, связанная при необходимости с несколькими кабельными трассами. Наличие кабеля не создаёт штробу автоматически. Кабельная длина не подменяет длину штробления.

Повторно нарисованные коллинеарные перекрывающиеся интервалы на одной стене/плоскости можно объединить после подтверждения при одинаковом сечении и режиме заделки. Для перекрытий с разной геометрией, шириной или режимом заделки требуется явное разрешение конфликта. Простое суммирование дублей запрещено. В местах пересечения различных штроб v1 допускает погонную оценку объёма без вычитания пересечения; показать это как способ оценки, не как точный объём 3D-тела.

Потенциальное штробление несущей или неизвестной конструкции помечается для отдельного инженерного согласования. Редактор не выдаёт техническое разрешение на изменение конструкций.

Работы по штроблению учитывают все активные штробы. Заделка, грунтовка и смесь учитывают только fillAfterInstallation=true.

## 14. Формулы материалов

### 14.1. Подрозетники и механизмы

Количество подрозетников = сумма mountCount точек, требующих подрозетников. Накладная розетка и светильник по умолчанию не создают подрозетник. Разные типы подрозетников группируются отдельно. Механизмы розеток/выключателей считаются по их фактическому числу; рамки по размеру блока — отдельный материал.

### 14.2. Крепёж открытой прокладки

Фиксированное правило пользователя: только открытая прокладка, шаг 500 мм, запас всегда +15%.

Единица расчёта — MountingRun: непрерывный открытый путь с одним способом крепления. Чисто визуальное разделение полилинии не начинает новый путь крепежа. Для длины L>0 число точек опоры n = ceil(L_mm / 500) + 1: опоры на обоих концах и промежуточные с шагом не более 500 мм. Для L=0 результат 0. Выбор опор на обоих концах — зафиксированное допущение этого ТЗ.

При соединении частей одного MountingRun общая концевая опора считается один раз. Ветвления, крепёж общего лотка/пучка или общий кронштейн задаются отдельными mountingNodeId и считаются один раз по ID. Если у двух кабелей нет общей mountingGroupId, крепёж считается отдельным для каждого кабеля/рукава.

Для каждого SKU крепежа: Nbase = число уникальных точек опоры с учётом нормы деталей на опору; Npurchase = ceil(Nbase × 1,15). Сначала суммирование базы по SKU, затем один запас и одно округление.

Пример: один открытый прямой путь 2000 мм → ceil(2000/500)+1=5 опор → ceil(5×1,15)=6 креплений. Разделение пути на два отрезка 1000 мм при сохранении MountingRun даёт те же 6. Скрытая штроба длиной 2000 мм даёт 0 такого крепежа.

### 14.3. Метизы

NhardwareBase_sku = Σ(NuniqueMountingNodes × normPerNode) + Σ(прочие фактические узлы × norm). NhardwarePurchase_sku = ceil(NhardwareBase_sku × 1,15).

Считать от базы креплений до их запаса. Не умножать на 1,15 уже увеличенное число креплений: это скрыто удвоит запас. Пример: 5 опор, 2 метиза на опору → база 10 → ceil(11,5)=12 метизов. Запас крепежа и запас метизов независимы.

### 14.4. Грунтовка и смесь для заделки

Для каждой заделываемой штробы преобразовать L, w, d в метры.

- Оцениваемая площадь грунтования дна и двух боковин: A = L × (w + 2d), м². Торцы не включены; это принятая модель расхода, а не норматив.
- Грунтовка Qprimer = ΣA × расход_л_на_м² × число_слоёв.
- Геометрический объём заделки V = L × w × d, м³; v1 считает полный объём штробы без вычета кабеля.
- Смесь Qfiller = ΣV × расход_кг_на_м³.

Если производитель задаёт кг/(м²·мм), эквивалентная норма кг/м³ = значение ×1000. Нормы сохраняются вместе с единицами, источником и датой; не задавать неизвестный расход нулём.

Пример теста, не рекомендация материала: L=10 м, w=0,02 м, d=0,02 м; A=0,6 м², V=0,004 м³. При условных нормах 0,2 л/м² в один слой и 1000 кг/м³ получаем 0,12 л грунтовки и 4 кг смеси. При fillAfterInstallation=false оба значения 0; штробление остаётся 10 м.

Требуемое количество жидкости/смеси округлять вверх до 0,01 л/кг после суммирования по материалу. Если задан размер упаковки, отдельно показать число упаковок = ceil(required/packageSize), количество закупки = упаковки × packageSize. В стоимость включается закупаемое количество, а не два количества одновременно.

### 14.5. Материалы щита и ручные строки

Каждый фактический аппарат и корпус учитываются один раз по ID. УЗО, защищающее несколько линий, не размножается по числу линий. Дифавтомат не порождает дополнительно отдельные УЗО и автомат без такого решения в схеме. Резерв пустого места щита не создаёт автоматически покупку резервных аппаратов.

Ручные материалы явно помечены. Если такая строка дублирует автоматическую, пользователь выбирает «Замена количества» или «Дополнительное количество»; скрытое сложение запрещено.

## 15. Нагрузки, токи и фазы

Все результаты содержат входные данные, единицы, формулу, допущения и статус полноты. Это расчётный помощник; отсутствие части исходных данных не означает успешную проверку.

### 15.1. Мощности

Для нагрузки i: Pi_input = Pi, если задана электрическая входная мощность. Если задана механическая мощность, Pi_input=Pi/η при 0<η≤1. Мощность с таблички в Вт не делить на КПД повторно без основания.

Pinstalled_line = Σ(Pi_input × quantity_i). По умолчанию demandFactor_line=1. Расчётная активная мощность = Pinstalled_line × demandFactor_line. Коэффициент одновременности в диапазоне (0;1] задаётся явно с основанием; это отдельное значение от сложности работ. Не применять один коэффициент и на приборе, и повторно на линии скрытно.

### 15.2. Ток

При известном cosφ для каждой нагрузки:

- Однофазная: Ii = Pi_input / (U_LN × cosφ_i).
- Симметричная трёхфазная: Ii = Pi_input / (√3 × U_LL × cosφ_i).

Не применять трёхфазную формулу к произвольно несимметричному прибору; его фазные токи задаются отдельно по данным производителя. Нельзя делить мощность однофазной нагрузки на 380 В из-за трёхфазного ввода.

При смешанных cosφ в линии v1 использует консервативную сумму модулей токов нагрузок, затем явно заданный demandFactor_line. Это оценка для отбора кандидатов; подписать метод и не выдавать его за точный расчёт реактивной мощности. Для симметричного трёхфазного прибора его фазный ток добавляется на каждую из трёх фаз.

Примеры: 2200 Вт, 220 В, cosφ=1 → 10 А. 6600 Вт, 380 В, cosφ=1, симметричная 3ф → около 10,03 А на фазу. Отображать 2 знака после запятой, для сравнения с номиналом не использовать округлённое экранное значение.

### 15.3. Балансировка фаз

Балансировать расчётные токи, а не число линий. Сначала учесть трёхфазные нагрузки и вручную закреплённые однофазные линии. Остальные однофазные линии отсортировать по убыванию расчётного тока; при равенстве по стабильному ID. Каждую целую линию назначить фазе с минимальным текущим суммарным током; при равенстве порядок L1, L2, L3.

Это детерминированная эвристика, не гарантированный глобальный оптимум. Предпросмотр показывает «до/после» и максимальный фазный ток. Подтверждение применяет назначения; ручные закрепления не меняются. Перегрузку по вводу не скрывать перестановкой.

Показатель разбаланса для интерфейса: 100 × (Imax−Imin) / Iavg при Iavg>0; при нулевых токах 0. Порог предупреждения — пользовательская рекомендация профиля, не универсальный норматив. Ток нейтрали и гармоники таким показателем не проверяются.

## 16. Щит и подбор защиты

### 16.1. Модель

Panel содержит ввод, корпус, ряды, аппараты и связи. ProtectiveDevice имеет id, kind, materialSnapshot, ratedCurrentA, poles, modules, characteristic, breakingCapacityA, residualCurrentMa при наличии, residualType, upstreamDeviceId, protectedCircuitIds, origin=manual|suggested, verificationStatus. Ширина modules допускает шаг 0,5 модуля; для вычислений раскладки использовать целые полумодули, чтобы не терять реальные паспортные размеры.

Поддержать вводной аппарат, автоматы, УЗО, дифавтоматы, ручные дополнительные устройства, N/PE-шины и принадлежности. Для аппаратов задаются реальные паспортные ширины; не считать любой автомат одним модулем и любое УЗО двумя.

Линия ссылается на аппарат защиты от сверхтока и при необходимости на дифференциальную защиту. Один аппарат может защищать несколько ветвей только при явной проверяемой модели. Само число линий не является нормативной формулой числа автоматов. УЗО само по себе не считается защитой от сверхтока.

### 16.2. Рекомендация кабеля и аппарата

1. Проверить фазность, потребителей, расчётный ток, материал жил, изоляцию, число нагруженных жил, способ монтажа, температуру, совместную прокладку, наличие PE и входные ограничения.
2. Найти применимые записи разрешённого проверенного профиля. Нельзя заменять отсутствие условий одной универсальной таблицей «сечение → автомат».
3. Рассчитать длительно допустимый ток Iz по выбранному методу и применимым поправочным коэффициентам; сохранить идентификаторы таблиц и строк.
4. Сформировать кандидаты кабеля и аппаратов с проверкой координации защиты. В качестве части проверки перегрузки учитываются Ib ≤ In ≤ Iz и I2 ≤ 1,45×Iz при применимости соответствующего правила; источник и область действия обязательны [S6]–[S8]. Эти неравенства не заменяют проверки короткого замыкания и времени отключения.
5. Проверить условия применения, падение напряжения при наличии полноценного метода/данных, отключающую способность, требования дифзащиты и PE согласно профилю. Непроверенные условия перечислить отдельно.
6. Показать рекомендуемые варианты с основанием; применение — явное действие. Ручная замена повторно запускает проверки и сохраняет причину override.

Если данных или проверенного профиля нет, электрическая рекомендация получает статус «Недостаточно данных», а не зелёную галочку. Геометрия, работа со сметой и ручная комплектация щита продолжают работать. Эта ситуация должна быть отдельно описана в протоколе; нельзя объявить нормативную часть полностью готовой.

### 16.3. Раскладка

Показывать таблицу и ряды DIN. Разрешено перетаскивание аппаратов и редактирование порядка доступными кнопками. Не допускать наложения или размещения за границей ряда. Соединения/группы дифзащиты должны прослеживаться; это функциональная схема, не монтажная инструкция по подключению клемм.

Mused = сумма ширин установленных аппаратов и модульных принадлежностей. Mtarget = ceil(Mused × (1+reservePct/100)). Из каталога выбрать минимальный корпус с достаточной вместимостью и возможной раскладкой по рядам. Общего числа мест недостаточно, если многополюсный аппарат не помещается ни в один ряд. Невозможность разместить показать явно.

Пример: Mused=20, reserve=20% → Mtarget=24; корпус 24 модуля возможен только если раскладка по его рядам допустима. Резерв — настройка продукта. Запас 15% крепежа к модулям щита не относится.

## 17. Профили правил и проверка проекта

### 17.1. Разделение правил

Каждое правило имеет category: dataIntegrity, userRequirement, engineeringRecommendation, normativeConditional. Отдельно хранить status: verified, unverified, disabled. Нельзя автоматически объявлять любой ГОСТ безусловно юридически обязательным для любого объекта.

RuleProfile: id, name, version, jurisdiction, objectTypes, supplySystems, documents, rules, verifiedAt, verificationScope. Каждая нормативная запись содержит документ, редакцию, пункт/таблицу/строку, URL, условия применимости, входные величины, действие и известные ограничения. Код не исполняется из импортированного профиля: правила только в разрешённом декларативном формате.

Нормативную базу начинать с источников [S6], [S7] и проверяемых глав ПУЭ: допустимые токи, защита и заземление, жилые здания. Пункты ПУЭ, СП, правила для ванных и иные требования добавлять только после проверки доступного текста, области применения и актуальных изменений. На этапе этого ТЗ подтверждены официальные карточки двух ГОСТ; все их численные таблицы, конкретные пункты и остальные документы не объявляются проверенными автоматически.

Разработчик должен наполнить ограниченный рабочий профиль для явно описанных бытовых условий и приложить RULES_VERIFICATION.md с проверенными ссылками. Если исходники недоступны, зафиксировать конкретный блокер, не подставлять значения из памяти и не скрывать это в результатах. Наличие ручного режима не заменяет сдачу заявленного автоматического профиля.

### 17.2. Результаты

Каждый результат: code, severity=error|warning|info, objectType, objectId, message, reason, suggestedAction, sourceRuleId|null, blocksElectricalRelease, blocksClientEstimate.

Обязательные группы проверок:

- Геометрия: незамкнутое/самопересекающееся помещение, неверная высота, потерянная привязка, нулевая трасса, кабель без связности.
- Назначения: точка без линии, одна нагрузка в двух линиях, отсутствующий кабель/защита, несовместимая фазность.
- Исходные величины: неизвестная мощность, cosφ, КПД при необходимости, параметры ввода, условия допустимого тока.
- Электрика: перегрузка линии, несогласованность аппарата и кабеля, PE и дифзащита по применимому профилю, неоценённые ток КЗ/время отключения/селективность, конфликт ручного выбора.
- Технология: потолочный путь освещения, непроверенная конструкция для штробы, дубли штроб, открытый крепёж, неизвестная норма заделки, непроверенные хвосты кабеля.
- Смета: отрицательная сумма, отсутствующая цена, неподтверждённый override, несовместимые единицы, устаревшая версия расчёта.

### 17.3. Блокировки

Сохранение черновика доступно всегда при структурно сохраняемых данных. Структурно повреждённый импорт не сохранять поверх объекта.

Клиентская финальная смета блокируется финансовыми ошибками, отсутствующими ценами включённых строк, неразрешёнными дублированиями и устаревшим расчётом. Можно исключить нерасценённую строку только явно; это меняет состав и итог.

В режиме «По плану» отсутствующая трасса, неполная геометрия или неизвестная норма не превращаются в нулевое количество включённой строки. Такой объём требует заполнения, явной ручной оценки с отметкой либо исключения позиции до финальной сметы. В быстром режиме отсутствие плана ошибкой не является.

Непроверенные электротехнические условия не запрещают коммерческую смету: она не является разрешением на монтаж. На экране сохраняется список непроверенного, а при наличии таких условий в примечании PDF — «Коммерческий расчёт. Электротехнические решения требуют проверки». Финальный электротехнический отчёт с утверждением успешной проверки недоступен при ошибках/непроверенных обязательных условиях. Не требовать бессмысленного подтверждения при каждом сохранении.

## 19. Деньги, сложность и снимки цен

### 19.1. Формула

Деньги — копейки, ROUND_HALF_UP. Количество сохраняется в канонических единицах/допустимой точности и переводится в рациональный множитель для расчёта. Не складывать денежные значения через неограниченный binary float. Цена может иметь точность до копейки.

1. Стоимость строки = round_half_up(эффективное количество × цена за единицу в копейках).
2. W = сумма строк работ, включая дополнительные работы, классифицированные как работы.
3. Wc = round_half_up(W × Kcomplexity). Коэффициент применяется ровно один раз к общей стоимости работ.
4. M = сумма строк материалов, включая ручные материалы и учитывая фасовку.
5. B = Wc + (includeMaterials ? M : 0).
6. A = round_half_up(B × markupBasisPoints / 10000).
7. S = B + A.
8. D = round_half_up(S × discountBasisPoints / 10000) либо фиксированная скидка в копейках, выбран ровно один вид.
9. T = S − D. Фиксированная скидка больше S является ошибкой ввода.

Физические количества, мощность, ток и закупочный запас не умножаются на сложность. Наценка и скидка относятся к включённой коммерческой сумме. Налоги не вычислять автоматически; налоговый статус и пояснение, если нужны, вводятся текстом без выдуманного расчёта.

Пример: W=10 000 ₽, K=1,2, M=5000 ₽, материалы включены → B=17 000 ₽. Наценка 10% → S=18 700 ₽. Скидка 5% → T=17 765 ₽. Материалы исключены → B=12 000 ₽; остальные действия применяются к этой базе.

### 19.2. Snapshot

Изменение глобального прайса не меняет ни сохранённую смету, ни уже выбранные цены активного объекта автоматически. «Обновить цены из прайса» показывает отличия и создаёт новую расчётную ревизию после явного применения.

EstimateVersion фиксирует данные клиента и исполнителя, строки/количества/цены, нормы, настройки, коэффициенты, правила, результаты расчётов, итог и публичное представление. Все ссылки, нужные для восстановления результата, дополнены снимками значений. Версия неизменяема; исправление создаёт следующую.

Актуальный черновик и сохранённая версия визуально различаются. Переименование библиотеки или изменение телефона исполнителя не переписывает PDF старой версии. PDF можно воспроизвести из её снимка без текущего прайса.

## 20. Клиентский PDF

### 20.1. Обязательное содержание

Заголовок «Смета на электромонтажные работы», номер и дата, исполнитель и телефон, заказчик и телефон при наличии, адрес/название объекта, площадь при наличии, перечень работ, единицы и объёмы. Материалы — отдельный перечень названий/количеств/единиц, если includeMaterials=true. Внизу одна общая итоговая сумма в рублях, примечание, опциональные места подписей сторон.

Две финансовые формы «внутренний расчёт» и «клиентский PDF» не должны использовать один и тот же полный объект данных. Функция buildClientEstimateDTO выбирает только разрешённые поля. Публичные строки: name, quantity, unit. Общий totalKopecks передаётся один раз.

### 20.2. Строгие ограничения

- Нет цены за единицу.
- Нет стоимости строки, работы, этапа или материала.
- Нет отдельных финансовых подытогов «Работы»/«Материалы».
- Нет внутреннего коэффициента, размера наценки и построчной скидки.
- Нет строки «Срок выполнения», плановой даты завершения или замаскированного аналога срока.
- Перечень работ и объёмы остаются видны.
- Внутренние расценки отсутствуют также в скрытом тексте, метаданных и вложениях PDF, а не только замаскированы CSS.

### 20.3. Генерация и отправка

PDF создаётся локально как Blob из снимка сметы. Использовать локально встроенный шрифт с кириллицей и знаком ₽; ASCII-шрифты jsPDF сами по себе не обеспечивают эти символы [S4]. Текст остаётся выделяемым; основной документ не является скриншотом интерфейса.

A4, портретная ориентация, поля не менее 15 мм, основной шрифт 10–12 pt, повтор заголовка таблицы, перенос длинных названий, номера страниц. Ширина столбца «Работа/материал» не менее 65% рабочей таблицы. Итог и подписи не перекрывают таблицу, длинный документ корректно разбивается на страницы.

«Скачать PDF» сохраняет estimate_<номер>_<YYYY-MM-DD>_v<версия>.pdf. «Поделиться» применяет navigator.canShare({files}) и navigator.share только при поддержке; иначе предлагает скачивание. Отмена пользователем не является ошибкой генерации. Не отправлять документ в мессенджер автоматически.

Дополнительная печатная HTML-форма использует тот же публичный DTO и print.css с @media print и @page [S5]. Печать браузером — дополнительный путь; она не заменяет обязательную генерацию скачиваемого PDF. Предпросмотр должен показывать именно публичную форму.

План и схема щита при необходимости экспортируются отдельно как SVG/PNG с масштабной линейкой и маркировкой. Они не вставляются в смету автоматически. Печать «в масштабе» возможна только с явной настройкой страницы; не обещать размер 1:1 на листе для произвольного плана.

### 21.2. Статусы и удаление

Статусы объекта: «Замер», «Смета», «Смета отправлена», «Согласовано», «В работе», «Завершено». Меняет пользователь, скачивание/отправка через системное меню не доказывает получение и не меняет статус автоматически.

Удаление объекта сначала перемещает его в корзину; восстановление доступно. Безвозвратная очистка корзины — отдельное явное действие с количеством объектов. Дубликат получает новый projectId и новые внутренние ID с полной перенастройкой ссылок; старые версии смет остаются у оригинала, у дубликата создаётся новый черновик.

Архивирование справочника не ломает snapshots. При физическом удалении неиспользуемой записи проверить все ссылки; используемую разрешено только архивировать.

## 22. Состояние, пересчёт и сохранение

Единственный источник изменяемых данных — store. UI отправляет команды, валидаторы проверяют их, reducer/handler меняет модель. Калькуляторы не читают DOM и не пишут в IndexedDB. Производные показатели пересчитываются из данных, а не являются независимыми редактируемыми «истинами».

Порядок расчёта: геометрия → физические кабели/штробы → нагрузки → доступные рекомендации защиты → щит → материалы/работы → цены → публичный DTO. Циклическая зависимость стоимости и электрических параметров запрещена.

Длительный расчёт получает sourceRevision. Если объект изменился до завершения, результат старой ревизии отбрасывается. Повторный расчёт одной ревизии детерминирован. Изменение высоты/прибора/цены помечает соответствующие результаты устаревшими.

Автосохранение после подтверждённой команды, debounce не более 800 мс; команды перетаскивания сохраняются после завершения жеста. На pagehide/visibilitychange попытаться сбросить очередь, но не полагаться только на события закрытия. Транзакционно сохранять цельный ProjectDocument с вложенными сущностями. Библиотеки/настройки/версии — отдельные stores IndexedDB; создание версии и связанного индекса атомарно.

Хранилища: projects, estimateVersions, catalogs, priceLists, ruleProfiles, settings, assets, pdfArtifacts. projectId и versionNo индексируются. Миграции БД версионируются, сначала проверяются на копии. Не очищать всю БД при ошибке миграции.

Несколько вкладок: обнаруживать через BroadcastChannel и revision, при возможности Web Locks. Устаревшая вкладка не перезаписывает более новую ревизию. Предложить перечитать либо сохранить независимую копию. В приложении с одним пользователем это предотвращение потери данных, а не облачная совместная работа.

## 23. Импорт, экспорт и резервные копии

Обязательны экспорт одного объекта и полная резервная копия приложения в JSON. Оболочка: format="elektrosmeta-backup", schemaVersion, appVersion, exportedAt, projects, estimateVersions, catalogs, prices, settings, ruleProfiles, assets, optionalPdfArtifacts.

Логотипы и обязательные бинарные активы включать как base64 с MIME; PDF можно не включать, если точное публичное содержимое воспроизводится из снимка и используемый шрифт/версия генератора сохранены. В интерфейсе пояснить состав копии. Не называть файл полноценной копией, если в нём отсутствуют применённые цены, библиотеки или нормы.

Перед импортом: размер, JSON.parse, schemaVersion, белый список полей/типов, конечность чисел, целостность ссылок, лимиты массивов, корректность денежных единиц, MIME активов. Не выполнять строки как код. Файлы новее поддерживаемой схемы отклонять с объяснением; старые мигрировать через проверенный адаптер.

Предпросмотр показывает число объектов, смет, библиотечных записей и конфликты. Режимы: «Добавить как копии» с remap всех ID; «Восстановить полную копию» с предварительным экспортом текущих данных и отдельным подтверждением замены. Не перетирать объекты совпавшими ID по умолчанию. Применение транзакционное; при ошибке исходные данные остаются.

Стартовые лимиты: 50 МБ на JSON, 5 МБ на логотип, 10 000 объектов модели в одном проекте, не более 100 000 вершин суммарно на проект. Превышение — понятный отказ, а не зависание. Лимиты можно менять в технической конфигурации после проверки производительности.

Установка PWA и IndexedDB не гарантируют сохранность при очистке браузера. Реализовать экспорт, дату последней копии и доступную опцию persistent storage через feature detection; не обещать вечное хранение [S1]. В приватном режиме недоступность хранилища не маскировать.

## 24. Офлайн, ошибки и восстановление

После первой полной загрузки кешировать оболочку, модули JS/CSS, локальные vendor-файлы, шрифты, иконки и стартовые справочники. Личные проекты хранятся в IndexedDB, а не в общем HTTP-кеше. Офлайн CRUD, план, расчёты, библиотеки и PDF не выполняют сетевых запросов.

Service Worker работает для HTTPS/localhost [S2]; HTTP по IP в локальной сети и file:// не обещают установку/офлайн-PWA. Онлайн-первая загрузка не считается офлайн-проверкой: проверить повторный запуск после отключения сети.

Кеш приложения версионировать. Новая версия активируется после безопасного сохранения текущего черновика; показать возможность обновления. Старый кеш удалять после успешной активации, данные IndexedDB не очищать. Не кешировать неуспешные HTTP-ответы как готовую оболочку.

При quota exceeded, запрете хранилища или сбое транзакции: сохранить доступный черновик в памяти, показать «Не удалось сохранить», предложить экспорт и повтор. Не выводить «Сохранено». При повреждённом объекте открывать список остальных и предлагать экспорт проблемной записи для восстановления.

Ошибка PDF не меняет версию сметы и не удаляет предыдущий PDF. Ошибка сети при обновлении не блокирует уже установленное приложение. Ошибки логируются локально без телефона, адреса, имени и полного содержимого сметы; экспорт диагностики по явному действию.

## 25. Интерфейс, доступность, безопасность и производительность

### 25.1. Интерфейс

Рабочий стиль: светлый фон, тёмный читаемый текст, один акцентный цвет, крупные числа итога. Названия работ переносятся, поля не перекрываются. На ширине 360 px строки сметы становятся карточками; горизонтальный скролл всей страницы запрещён. Сам чертёж панорамируется внутри редактора.

Основные зоны касания не меньше 44×44 CSS px; шрифт форм не меньше 16 px на телефоне. Контраст текста не ниже 4,5:1. Подписи полей постоянны, ошибки связаны с полем, клавиатурный фокус видим, диалоги удерживают фокус и возвращают его при закрытии. Цвет линий дублируется номером; предупреждения — текстом и значком. Списочный редактор координат/размеров доступен как альтернатива точному перетаскиванию.

### 25.2. Защита данных

Клиентские сведения остаются на устройстве до явного экспорта/отправки. Нет аналитических пикселей, телеметрии и внешней отправки форм. Текст выводить через textContent/безопасные DOM-операции; не вставлять пользовательский HTML. Без eval и Function из импорта. Логотип только PNG/JPEG/WebP, при необходимости перекодировать в растровое изображение; активный SVG не принимать как пользовательский логотип.

Content Security Policy совместима с локальными модулями и PDF; запретить произвольные внешние источники. Web Share только по пользовательскому нажатию. Отмена скачивания/печати не меняет статус договора или объекта. Резервный JSON содержит персональные данные; не публиковать его автоматически.

### 25.3. Производительность

Контрольная нагрузка: 200 стен, 50 помещений, 500 точек, 100 линий, 1000 сегментов трасс, 300 штроб. На тестовом Android 14 обеспечить видимую реакцию на обычное действие до 100 мс и рабочую частоту pan/zoom не ниже 30 FPS; полный пересчёт этого набора целевой до 1 с, PDF 300 строк — до 5 с. Это измеряемые цели, фактические результаты записать с моделью устройства/браузером.

Перемещение перерисовывать через requestAnimationFrame, не делать полную регенерацию DOM на каждый pointermove. Сложные вычисления при необходимости выносить в Web Worker с revision-guard. Лимиты памяти проверять; предпросмотры и PDF не держать безгранично в памяти. UI показывает действие «Расчёт» без фиктивного процента, если точный прогресс неизвестен.

## 29. Definition of Done и передача результата

Разработка считается завершённой, когда:

1. Выполнены обязательные функции раздела 2, есть рабочие сценарии A01–A25.
2. Пройдены тесты числовых алгоритмов, snapshots, импорта и публичного PDF.
3. Нормативный автоматический профиль имеет ограниченную, но реальную подтверждённую область действия и заполненный реестр источников. Непроверенные условия видны отдельно. Если это не выполнено, честно указать частичную готовность соответствующего модуля.
4. Проект запускается как статический сайт без обязательной сборки и работает после установки/кеширования офлайн.
5. Нет ошибок консоли в основных сценариях, фиктивных кнопок, случайных демо-цен в реальных объектах и скрытых сетевых зависимостей.
6. Имеются README, инструкция пользователю, реестр зависимостей/лицензий, протокол приёмки с датой/средой и TRACEABILITY.md.
7. Пользовательские данные и старые сметы переживают обновление прайса и приложения.
8. Исходные файлы и локальные ресурсы приложены; подготовлена папка, пригодная для статического размещения. Реальное размещение — только по отдельному запросу.

В финальном сообщении разработчика: как запустить, что реализовано, какие проверки фактически выполнены и какие конкретные ограничения остались. Не писать «всё соответствует ПУЭ» и не заявлять проверки на физическом устройстве, если была только эмуляция.
